01 — what a censor sees

Two kinds of observer

A censor can watch a connection, or it can poke at the server. Samizdat is built so that both see a browser and a website. The client connects to the server's IP address and names a cover site in the TLS handshake. The server is not that site. It holds the key to tell its own clients from everyone else, and hands everyone else to the real cover site.

Watching the wire

  1. A TLS 1.3 ClientHello from uTLS with Chrome's fingerprint, naming the cover site.
  2. The authentication tag is the 32-byte SessionID that every TLS 1.3 ClientHello carries anyway. It's sealed to the server's key and to that exact ClientHello, and no part of it repeats between connections.
  3. The first ten TLS records after the handshake follow sizes and directions drawn from a model of real TLS flows, not the fixed opening of an HTTP/2 tunnel.
  4. After that, one long-lived HTTP/2 connection carries every tunnelled stream, like a browser's.

Probing the server

  1. Any ClientHello without a valid tag, or one that has already been used, is forwarded byte for byte to the real cover site.
  2. The prober completes a real handshake with the cover site's real certificate and gets its real HTTP responses. The server never parses them.
  3. Replaying a captured ClientHello doesn't work either: the server remembers every SessionID it has accepted for 24 to 48 hours, and a version 2 tag expires 12 hours either side of the server's clock.
  4. Clients can pin the server's certificate, so a client that's been sent to the cover site fails instead of talking to it.
02 — the first packets give it away

What CenKL found

In late 2025, researchers at the University of Michigan and elsewhere recorded 326,531,763 real TLS flows at a regional ISP and built a model of how real TLS connections begin: the size and direction of each packet after the handshake. They then measured how far nine circumvention protocols stray from it, using KL divergence (in nats; 0 means identical).

Their conclusion: all of them are distinguishable from real-world TLS, as early as the first post-handshake packet.

1208 bytes

Trojan, VMess, VLESS and XTLS Vision send unusually many 1,208-byte packets in their first three packets after the handshake. Real TLS does that at the first packet only 0.38% of the time. The cause is Go's dynamic TLS record sizing, which Xray leaves on.

The authors' countermeasure, ProxyShaper, reshapes a connection's first 10 TLS records with sizes and directions drawn from their model. Against VLESS, it cut a gradient-boosted classifier's precision from 0.977 to 0.830. It helps; it doesn't make a proxy invisible.

Samizdat, measured against the same model

Samizdat now does what ProxyShaper does, by default at both ends. Both sides derive a shared seed from the TLS session's exported keying material, draw the same ten-record schedule from CenKL's released order-1 Markov model, and send exactly those record sizes in those directions, carrying HTTP/2 data inside and padding the rest. It also turns off Go's dynamic record sizing and drops TLS session tickets, which added a tell of their own.

Nats of KL divergence from CenKL's size-and-direction model, first 10 packets after the handshake, 800 flows each on loopback, segmented at a 1,448-byte MSS. The floor isn't zero because 800 flows is a finite sample: real TLS drawn from the model itself scores 11.3. These are our measurements with the authors' released model, not the paper's; see samizdat#29.

The 1,448-byte cap matters. CenKL's model counts 1,460-byte packets, from senders without TCP timestamps. Linux servers send timestamps and fit 1,448 bytes, so a scheduled 1,460-byte record leaves as two packets, 1,448 and 12. The paper notes the same mismatch in its own testbed. Samizdat leaves sizes above 1,448 out of the schedule.

REALITY is the closest relative

Samizdat's version 2 authentication is REALITY's idea, implemented independently: an X25519 secret between the client's ordinary key share and the server's static key, an AES-GCM seal over a time and a short ID, and the whole ClientHello as associated data, so a copied tag fails in any other handshake. The differences are in what surrounds it: samizdat remembers what it has accepted, checks the time by default, doesn't need the cover site to be reachable for its own clients, multiplexes over HTTP/2, and shapes the start of the connection. REALITY hands authenticated clients a throwaway certificate signed with the shared key; samizdat serves its own and lets clients pin it.

04 — under the hood

How it works

AAuthentication in the SessionID

The client takes an X25519 secret between its own key share and the server's public key, derives an AES-256-GCM key with HKDF over the ClientHello's random, and seals version ‖ time ‖ short ID with the rest of the ClientHello as associated data. The 32 bytes that come out replace the SessionID. Older clients send version 1, an HMAC tag; servers accept both until told otherwise.

BMasquerade

A connection that doesn't authenticate is spliced, raw, to the cover site's real address. The server buffers only the ClientHello it read to decide, replays it to the cover site, and copies bytes both ways until either side closes. It never parses or alters them.

CConnection-start shaping

Both ends export keying material from the finished TLS session. 32 bytes seed a ChaCha8 sampler that draws ten records' sizes and directions from the model; 8 bytes become a marker that tells the server this client shapes. During the schedule each side sends exactly its scheduled records, carrying queued HTTP/2 bytes and padding. After the tenth, data passes straight through.

DOne connection, many streams

Every proxied connection is an HTTP/2 CONNECT stream on one long-lived TLS connection, so a censor counting TLS connections to an address sees one. Servers run samizdat's own lean HTTP/2 server, which batches frames into fewer TLS records and system calls: 66–90% less server CPU per gigabyte downloaded than Go's standard one in benchmarks, with the same frames on the wire.

EFragmented ClientHello

Optionally, the ClientHello is split across TCP segments at the SNI, with a short random delay, in the style of Geneva. A middlebox that reads the SNI from a single packet doesn't find it there.

FLegacy clients keep working

A server reads the first 8 bytes after the handshake. The shaping marker means a shaping client; an HTTP/2 preface means an older one, which is served exactly as before. New servers serve every client released so far; new clients need new servers.

05 — what it doesn't do

Limits

No proxy that carries real traffic is invisible. These are the gaps we know about.

  • Timing isn't shaped. CenKL's timing-aware classifier still reaches about 0.9 recall against shaped traffic. Samizdat's 1–30 ms random jitter isn't a fix: Xue et al. (NDSS 2025) found that random delays like obfs4's can make cross-layer RTT fingerprinting easier, not harder.
  • Tunnelled TLS is still inside. Applications using samizdat bring their own TLS, so there is TLS inside samizdat's TLS. Multiplexing helps most when several streams share the connection; Xue et al. (USENIX Security 2024) found it far weaker with only one.
  • Shaping covers ten records. After that, traffic is whatever the tunnelled applications send. The schedule fixes TLS record sizes; TCP can still split or merge them into packets.
  • The model is one network's view. It was built from one regional ISP in late 2025. Real TLS elsewhere, or later, may look different, and a censor with its own data can build its own model.
  • The replay record lives in memory. A server restart forgets the SessionIDs it has accepted. Version 2's 12-hour time limit still applies.
  • Not independently reviewed. The version 2 authentication hasn't had an outside cryptographic review, and the measurements on this page are ours, on loopback.
06 — use it

Use it

Samizdat is a Go library with no sing-box dependency, and an inbound and outbound in lantern-box. Lantern's apps use it today.

go get github.com/getlantern/samizdat

client, err := samizdat.NewClient(samizdat.ClientConfig{
    ServerAddr:  "203.0.113.7:443",
    ServerName:  "cover.example",   // the cover site named in the handshake
    PublicKey:   serverPublicKey,   // 32-byte X25519 public key
    ShortID:     shortID,           // 8-byte client identifier
    Fingerprint: "chrome",
})
conn, err := client.DialContext(ctx, "tcp", "example.com:443")
// lantern-box (sing-box) outbound
{
  "type": "samizdat",
  "tag": "samizdat-out",
  "server": "203.0.113.7",
  "server_port": 443,
  "public_key": "<64 hex chars>",
  "short_id": "<16 hex chars>",
  "server_name": "cover.example",
  "cert_spki_sha256": "<optional pin, 64 hex chars>"
}

Generate keys with go run ./cmd/samizdat-server --genkeys. Pick a cover site that's reachable from the server, serves TLS 1.3 with HTTP/2, and is unremarkable on the network you're getting around.
